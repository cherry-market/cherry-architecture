# ADR-002: 이미지 수정 범위

- **상태**: 확정
- **일자**: 2026-02-09
- **참여**: Claude (코드베이스 분석, 비용 산출) + ChatGPT (리서치/사례 조사)

---

## 맥락 (Context)

상품 수정 기능에서 이미지를 어디까지 수정할 수 있게 할 것인지 결정이 필요했다.

현재 이미지 파이프라인:
- Presigned URL로 S3 직접 업로드 (최대 10장)
- Lambda가 리사이즈 처리 (detail 1280px, thumbnail 256x256)
- 각 이미지는 `imageOrder`(순서)와 `isThumbnail`(썸네일 지정) 값 보유
- 현재 Lambda는 **조건부 thumbnail 생성**: imageKey의 `t/f` 플래그로 첫 번째 이미지만 thumbnail 생성
- 이미지 처리 완료 전까지 상품은 PENDING 상태

---

## 선택지 (Options)

| 선택지 | 설명 | 구현 복잡도 |
|--------|------|------------|
| **A) 텍스트만 수정** | 이미지 수정 불가, 삭제 후 재등록 유도 | 낮음 |
| **B) 이미지 추가/삭제만** | 순서 변경 없음, 썸네일 삭제 시 자동 승격 | 중간 |
| **C) 추가/삭제/순서변경/썸네일 재지정** | 완전한 UX, 당근마켓 수준 | 높음 |

### 비용 비교

| 선택지 | 개발 공수 | UX 품질 | 서비스 완성도 |
|--------|-----------|---------|------------------|
| A | 0.5일 | 빈약 ("이미지 파이프라인 만들고 수정 불가?") | 낮음 |
| B | 2~3일 | 보통 (대표 사진 교체 니즈 미충족) | 중간 |
| C | 3~5일 | 자연스러움 (실서비스 수준) | 높음 |

### Lambda 썸네일 정책 변경 비용

C안 채택 시, 썸네일 재지정을 위해 Lambda 수정이 필요:

| 방안 | 설명 | 비용 |
|------|------|------|
| **모든 이미지에 thumbnail 생성** | Lambda에서 `t/f` 조건 제거 | Lambda 코드 수정 1시간 |
| 재지정 시 Lambda 재트리거 | 새 워크플로우 필요 | 설계 + 구현 1~2일 |
| detail URL을 fallback | thumbnailUrl 없으면 detail 사용 | 코드 변경 30분, 성능 손해 |

**S3 추가 비용 (thumbnail 전체 생성 시):**
- thumbnail 1장: 5~20KB
- 상품당 추가 9장: 약 90~180KB
- 기존 원본+detail 대비 비중: **0.2~0.9%**
- 상품 1만 개 기준 월 추가 비용: **약 $0.02**

---

## 결정 (Decision)

**C) 추가/삭제/순서변경/썸네일 재지정**을 채택한다.

추가 결정:
- **PENDING 상태에서는 이미지 편집 불가** (Lambda 콜백과의 경합 방지)
- **Lambda를 모든 이미지에 thumbnail 생성하도록 변경** (기존 `t/f` 조건부 생성 제거)
- 썸네일 재지정은 DB `isThumbnail` 플래그 변경만으로 처리 (추가 리사이즈 불필요)

---

## 트레이드오프 (Trade-offs)

### 감수하는 것
- A/B 대비 구현 공수 증가 (프론트 드래그앤드롭 순서변경 등)
- Lambda 코드 수정 필요 (조건부 → 전체 thumbnail 생성)
- S3 스토리지 미세 증가 (월 $0.02 수준, 무시 가능)

### 얻는 것
- 당근마켓 수준의 완전한 이미지 편집 UX
- "S3 Presigned + Lambda 리사이즈 + PENDING + 메타데이터 정합성"까지 완전한 이미지 편집 UX 구현
- 썸네일 재지정이 DB 플래그 변경으로 단순화 (Lambda 재트리거 불필요)
