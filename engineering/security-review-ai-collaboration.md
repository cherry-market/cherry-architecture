# 보안 감사 기록: AI-인간 협업으로 발견한 인증 취약점

> **작성일**: 2026-04-15
> **배경**: Phase 10 (소셜 로그인 — Google/Kakao) 개발 중
> **결과물**: [ADR-010](../decisions/ADR-010-auth-user-enumeration-hardening.md)
> **분류**: 개발 프로세스 기록 / 포트폴리오

---

## 문서 목적

이 문서는 Cherry 프로젝트에서 AI 어시스턴트와 개발자가 **보안 취약점을 함께 발견하고 수정한 실제 사례**를 기록한다. 결과물인 코드 변경만 보면 드러나지 않는 "어떻게 문제에 도달했는가"와 "어떤 판단을 사람이 했는가"를 남겨, 향후 유사한 보안 검토에 참고하고 나아가 AI 활용 방식의 재현 가능한 패턴으로 정착시키는 것이 목적이다.

AI를 "버그 수정 자동화 도구"가 아닌 **의사결정 보조자**로 사용한 대표 사례이기 때문에, 개발 프로세스 기록으로 남길 가치가 있다고 판단했다.

---

## 발단

소셜 로그인 기능 구현의 마지막 단계에서 로컬 E2E 테스트를 진행하던 중, 개발자는 AI가 제안한 한 가지 프론트엔드 수정을 보고 **본능적으로 위화감**을 느꼈다. 당시 문제가 된 수정은 다음과 같다:

> Google로 가입한 사용자가 실수로 이메일/비밀번호 로그인 화면에서 로그인 시도를 하면, 프론트엔드가 백엔드 에러 메시지를 사용자에게 그대로 노출하여 "이 계정은 Google로 가입되어 있습니다"를 안내한다.

이 수정은 원래 "UX 버그 수정"으로 분류되어 있었다. 사용자 입장에서 정확한 안내가 나가므로 자연스러운 개선처럼 보였다. 그러나 개발자는 다음과 같이 반응했다:

> "이거 해당 아이디가 맞았고 구글 계정이라고 해서 특정인을 찾을 수 있는 보안 이슈입니다. (...) 차라리 로컬 스토리지에 최근 로그인을 무엇으로 했는지 저장해서 (...) 구글 로그인 버튼에 말풍선 UI가 하나 나와서 최근에 로그인 했다고 안내 하는게 좋습니다. (...) 보안 부분 다시 검토해봐요."

이 한 문장이 단순 UX 수정이었던 작업을 **전면 보안 감사**로 전환시켰다. 이 시점이 이번 협업에서 가장 중요한 전환점이다. AI는 "사용자 친화 메시지"라는 국소 최적화를 제안했지만, 사람은 "이 정보가 외부에 드러나면 공격 벡터가 된다"는 **시스템적 판단**을 내렸다.

## 감사 프로세스

### 1단계: 공격자 관점 재정의

요청에 따라 AI는 관점을 "기능 구현자"에서 "Red Team 감사자"로 전환했다. 구체적으로는 다음과 같이 사고 프레임을 바꿨다:

- "이 코드가 의도대로 동작하는가?" → "이 코드가 공격자에게 어떤 정보를 주는가?"
- "어떤 에러가 친절한가?" → "어떤 에러가 공격자에게 유용한가?"
- "이 로직이 맞는가?" → "이 로직이 동일한 시간에 실행되는가?"

이 관점 전환 후, 다음 3가지 공격 시나리오를 먼저 정의했다:

1. **타겟 피싱 공격** — 유출된 이메일 DB를 Cherry에 대입하여 Google 가입자 리스트를 선별한 뒤, 해당 사용자들에게 Google 사칭 피싱을 보내는 시나리오
2. **회원 리스트 구축** — 임의 이메일로 회원가입을 시도하여 응답 코드만으로 등록 여부를 판별하고 전체 회원 목록을 구축하는 시나리오
3. **타이밍 프로파일링** — 에러 메시지가 동일하더라도 응답 시간 차이만으로 계정 유형을 구별하는 시나리오

이 시나리오들을 **먼저 정의한 뒤**, 각 공격이 어느 코드 경로에서 입력값을 얻는지를 역추적하는 방식으로 조사 방향을 잡았다. 이는 "취약점이 보이면 추가로 찾는다"는 수동적 방식과 달리, **가설 주도적 감사(hypothesis-driven auditing)**에 가깝다.

### 2단계: 코드베이스 탐색

AI가 병렬로 수집한 조사 대상:

- `AuthService.login` / `AuthService.signup` (핵심 경로)
- `SocialAuthService`의 소셜 유저 검증 로직
- `SecurityConfig`의 URL 매칭 규칙과 permitAll 목록
- `JwtTokenProvider`의 알고리즘 검증 방식
- `CorsLocalDevConfig` / `CorsProdConfig`의 origin 화이트리스트
- 에러 응답 구조 (`GlobalExceptionHandler`, `ErrorResponse`)
- `ErrorCode` enum에 정의된 에러 메시지 문구
- Rate limit 구조 (IP 기반 / 계정 기반 존재 여부)
- `UserResponse`가 공개 엔드포인트에서 노출하는 필드

이 조사는 사람이 직접 했다면 최소 2-3시간이 걸렸을 분량을 AI가 수십 분 내에 병렬 탐색으로 마쳤다. 탐색 결과는 개별 발견 사항이 아니라 **"이 시스템의 보안 표면(surface)"** 전체를 한 장의 지도로 보여주는 형태로 정리되었다.

### 3단계: 취약점 정리 및 우선순위화

AI는 발견한 이슈 7건을 다음 축으로 분류했다:

| 축 | 기준 |
|---|------|
| 공격 가치 | 공격자가 얻는 정보량 / 공격 체인에서의 기여도 |
| 악용 난이도 | 필요한 선행 조건 / 자원 |
| 수정 복잡도 | 영향 받는 파일 수 / 로직 변경 규모 |
| UX 영향 | 정상 사용자 경험에 미치는 악영향 |

심각도는 OWASP-스타일로 Critical / Medium / Low로 표기하되, **실제 악용 가능성과 공격 가치**를 기준으로 조정했다. 예를 들어 "JWT 알고리즘 명시 고정 부재"는 이론적으로 Low로 분류될 수 있지만, 현재 라이브러리 버전에서는 **이미 안전**하다는 사실을 AI가 공식 문서를 확인하여 "추가 코드 변경 없음 + 주석화"로 결론냈다. 이는 "일단 고치자"식 과잉 수정을 피한 좋은 예이다.

### 4단계: 사람 검토 및 스코프 결정

AI의 리포트를 받은 사람은 다음과 같이 응답했다:

> "V-5~7 작업은 따로 이슈로 빼야하는 이유가 있나요?"

이 질문이 두 번째 중요한 분기점이다. 사람은 **AI의 보수적 권장을 되짚어** "이걸 이번 PR에 포함하지 말아야 할 실질적 이유가 있는가?"라고 되물었다. AI는 정직하게 재평가하여 다음을 인정했다:

- 최초 분리 권장은 "PR 스코프 증가 우려"라는 보수적 원칙에 의한 것
- 실제로는 각 수정이 10~15줄 이내의 사소한 변경이며 리뷰 부담이 낮음
- **보안 일관성 관점에서는 한 PR에서 완결**하는 것이 오히려 바람직
- 포트폴리오 관점에서도 "완결된 보안 작업"이 더 강력한 내러티브

결론: 모든 수정을 한 PR에 포함하고, 각각을 별도 커밋으로 분리하는 방식을 선택했다. 이 재평가는 사람이 유도했고, AI는 자신의 최초 권장을 고집하지 않고 논리적으로 수정했다. **"AI가 권장한 방향"을 무비판적으로 따르지 않는 것**이 이 프로세스에서 가장 중요한 사람의 역할이었다.

### 5단계: 수정 적용

사람이 3가지 세부 질문(더미 해시 상수 방식 가능 여부, rate limit 설정값, 말풍선 문구)에 승인하자, AI는 다음 순서로 수정을 적용했다:

1. **ErrorCode 추가** (`EMAIL_DUPLICATE`) 및 사용되지 않을 코드(`SOCIAL_LOGIN_REQUIRED`) 제거
2. **`AuthService.login` 재작성** — constant-time + constant-response + 이메일 단위 rate limit
3. **`AuthService.signup`** — 한국어 ErrorCode 기반 에러로 통일
4. **CORS 로컬 설정** — 명시적 origin 화이트리스트
5. **JWT 파서 주석** — 불변성에 의존하고 있음을 명시
6. **프론트엔드 롤백** — "provider 노출 메시지" 분기 제거
7. **최근 로그인 수단 유틸 + 말풍선 UX** — 업계 표준 패턴 도입
8. **5개 로그인 성공 지점 일괄 수정** — 각 플로우에서 `saveLastLoginMethod` 호출

각 변경 후 TypeScript 타입체크와 Gradle `compileJava`를 병렬로 실행하여 회귀를 즉시 검증했다.

### 6단계: 로컬 E2E 검증

수정이 완료된 뒤 다음 시나리오로 로컬 검증을 수행했다:

- (a) 존재하지 않는 이메일로 로그인 → 일반 메시지
- (b) Google 가입자의 이메일로 비밀번호 로그인 시도 → **같은** 일반 메시지
- (c) 정상 로컬 사용자의 비밀번호 오타 → **같은** 일반 메시지
- (d) 이미 가입된 이메일로 회원가입 → 한국어 에러
- (e) Google 로그인 성공 후 로그아웃 → 로그인 페이지에 말풍선 "최근에 여기로 로그인했어요" 표시

(a), (b), (c) 세 경우가 **사용자 시선과 응답 시간 모두에서 구분 불가**해야 한다는 것이 이번 수정의 핵심 성공 조건이었다.

## AI-인간 협업 패턴 분석

### AI가 잘한 것

| 항목 | 설명 |
|------|------|
| **빠른 병렬 탐색** | 10개 이상의 파일을 동시 조회하여 보안 표면을 빠르게 매핑 |
| **공격 시나리오 역추적** | 발견한 취약점을 실제 공격 체인과 연결하여 심각도 판단에 근거 제공 |
| **권장 근거 명시** | 매 결정마다 "왜 이 방식을 택하는가"와 "감수하는 것"을 동시에 제시 |
| **공식 문서 재확인** | JWT 알고리즘 고정 건에서, 자체 지식만으로 판단하지 않고 라이브러리 문서를 재확인하여 "수정 불필요" 결론 |
| **재평가 수용** | 사람의 되물음에 방어적으로 반응하지 않고, 최초 권장(스코프 분리)의 근거를 재검토하여 더 나은 방향(한 PR 집약)으로 수정 |
| **구체적 대안 제시** | 문제만 지적하지 않고, 구현 가능한 코드 형태까지 함께 제시하여 사람의 결정 부담을 줄임 |

### 사람이 반드시 해야 했던 것

| 항목 | 사람의 판단 |
|------|------------|
| **관점 전환 지시** | "이건 보안 이슈야" — 이 한 문장이 전체 감사를 트리거. AI는 "UX 수정"이라는 원래 프레임 안에서는 이 판단에 도달하지 못했다. |
| **스코프 재평가 유도** | "이걸 따로 뺄 이유가 있나?"라는 질문으로 AI의 보수적 기본값을 깨뜨림. |
| **정책적 판단** | Rate limit 수치, 말풍선 문구 같은 **서비스 톤앤매너와 관련된 결정**은 전적으로 사람이 결정. |
| **우선순위 재조정** | "이메일 확인 메일 기반 가입"처럼 MVP 스코프 외 작업의 배제 판단. AI는 "Critical이면 지금 고치는 게 맞지 않느냐"는 공격적 의견을 낼 수 있지만, 사람이 "MVP에 과설계"라고 브레이크를 걸었다. |
| **리스크 승인** | 이 수정이 실수로 정상 로그인을 차단할 위험이 없는지 최종 판단. |

### 실패했을 수 있는 지점

- **AI가 최초에 "SOCIAL_LOGIN_REQUIRED 에러를 프론트에서 특수 처리"를 제안한 것 자체**가 첫 번째 실패 가능성이었다. 사람의 개입이 없었다면 이 수정은 그대로 머지되어 프로덕션에 올라갔을 것이다.
- 만약 사람이 "좋은 UX네"로 수용했다면, **정보 노출이 오히려 사용자 UI로 의도적으로 드러나는 방향**으로 굳어졌을 것이다.
- 이 사례는 **"AI가 만든 코드는 잘 컴파일되고 기능이 동작한다"는 1차 신호에만 의존하면 놓치는 보안 결함**이 존재함을 직접 보여준다.

## 재현 가능한 체크포인트

향후 Cherry 또는 다른 프로젝트에서 유사한 AI-보조 보안 감사를 수행할 때 참고할 수 있는 체크포인트:

### 인증 관련 코드 리뷰 시 항상 확인할 것

1. **실패 경로 통일성**: 로그인·가입 실패의 상태 코드·메시지·응답 시간이 모두 동일한가?
2. **타이밍 동등성**: 서로 다른 분기가 해시 연산 등 비용이 다른 작업을 수행하지는 않는가?
3. **Rate Limit 축**: IP 단독이 아니라 계정 단위 제한도 있는가?
4. **에러 메시지 검증**: provider, 가입 방식, 계정 존재 여부 같은 정보가 문구에 녹아 있지 않은가?
5. **CORS 와일드카드**: `*` + `allowCredentials(true)` 조합이 있는가? 프로덕션에서는 명시적 목록인가?
6. **JWT 파서**: verifyWith에 전달되는 키 타입이 알고리즘을 제한하고 있는가? "alg: none" 우회가 가능한가?
7. **공개 엔드포인트 응답 필드**: 비로그인도 호출 가능한 API가 이메일·전화번호 같은 PII를 노출하지 않는가?
8. **에러 메시지 국제화 일관성**: 일부 에러만 영어로 남아 있는가? (이는 보통 예외 처리 누락의 신호)

### AI 사용 시 지킨 원칙

- **결정은 사람** — 정책·우선순위·스코프는 AI의 권장을 반드시 되묻는다.
- **근거는 코드** — AI의 주장은 파일/줄 단위 근거와 함께 제시되어야 한다.
- **검증은 실행** — 컴파일·빌드·로컬 E2E 테스트는 매 변경마다 즉시 수행한다.
- **스코프는 합의** — AI가 "이것도 수정해야 합니다"라고 말할 때 먼저 **"왜 지금인가"**를 묻는다.
- **문서는 동시** — 수정과 함께 결정 기록을 남긴다. 이 문서와 ADR-010이 그 결과물이다.

## 결론

이번 감사는 "AI는 빠르지만 사람이 방향을 잡는다"라는 익숙한 표현을 구체적 사례로 증명했다. AI가 혼자 모든 취약점을 찾아내지는 못했고, 사람이 혼자라면 시간이 훨씬 오래 걸렸을 것이다. 두 역할이 겹치지 않고 보완되는 방식이 가장 효과적이었다.

특히 기억할 점은 **"AI의 첫 제안이 보안 결함이었다"**는 것이다. 이 사실 자체가 이번 기록을 남겨둘 충분한 이유다. AI는 도구이고, 도구는 검토 없이 사용되어서는 안 된다.
