# ADR-010: 인증 사용자 열거 방지 및 타이밍 사이드채널 차단

- **상태**: 확정
- **일자**: 2026-04-15
- **관련 Phase**: 10 (소셜 로그인 — Google/Kakao)

---

## 맥락 (Context)

Phase 10에서 Google/Kakao 소셜 로그인을 기존 이메일/비밀번호 인증에 통합했다. 이때 로그인 실패 응답을 분기하는 기존 설계가 **사용자 열거(user enumeration)** 및 **타이밍 사이드채널** 취약점을 내포하고 있음을 발견했다.

구체적으로 로그인 API는 다음 세 가지 실패 케이스를 서로 다른 응답으로 처리하고 있었다:

1. 존재하지 않는 이메일 → `401 "이메일 또는 비밀번호를 확인해주세요"`
2. 존재하는 이메일이지만 소셜 가입자 → `400 "GOOGLE(으)로 로그인해주세요"` (provider까지 노출)
3. 존재하는 이메일 + 비밀번호 불일치 → `401 "이메일 또는 비밀번호를 확인해주세요"`

공격 시나리오:

- **타겟 프로파일링**: 외부에서 확보한 이메일 리스트를 대입하여, 응답 상태 코드와 메시지만으로 "Cherry 등록자", "소셜 가입자", "사용 중인 provider"를 판별할 수 있다.
- **타이밍 분석**: 설령 모든 실패 메시지를 동일하게 만들어도, 로컬 유저 실패 경로만 bcrypt 해시 검증을 수행하므로 응답 시간에 큰 차이가 발생한다. 공격자는 타이밍 측정만으로 계정 유형을 구별할 수 있다.
- **타겟 피싱**: 위 정보를 토대로 특정 provider 가입자 리스트를 확보하면, 해당 provider를 사칭한 피싱 공격의 정확도가 크게 올라간다.

회원가입 API에도 유사한 문제가 있었다. 이미 가입된 이메일로 가입 시도 시 `409 Conflict`와 `"Email already in use."`를 반환하므로, 단순 상태 코드만으로 가입 여부를 100% 판별 가능했다.

CORS, JWT, Refresh Token 회전 로직 등 다른 인증 구성 요소도 함께 점검하여 동일 원칙(실패 응답·실패 시간 통일, 방어 심층화)이 지켜지는지 검증했다.

---

## 결정 드라이버 (Decision Drivers)

- **정보 비노출**: 로그인 실패 응답에서 "계정 존재 여부", "가입 유형(로컬/소셜)", "소셜 provider"가 드러나지 않아야 한다.
- **타이밍 상수성**: 실패 경로의 응답 시간이 계정 유형과 무관하게 일정해야 한다.
- **사용자 편의성 훼손 최소화**: 소셜 가입자가 과거 방식으로 로그인하려 할 때 스스로 올바른 수단을 찾을 수 있어야 한다.
- **스코프 경계**: 보안 일관성을 위해 근본 원인 수정은 같은 PR에서 완결한다. 운영 통계·로그 수집·고급 브루트포스 방어 같은 정책 영역은 별도 작업으로 분리한다.

## 주요 의사결정

### 1. 실패 응답 통일 (User Enumeration 방지)

| 선택지 | 장점 | 단점 |
|--------|------|------|
| 에러 코드/메시지 분기 유지 | 사용자가 원인을 즉시 파악 | provider 노출, 대규모 프로파일링 가능 |
| 상태 코드 통일 + 메시지 분기 | 최소 변경 | 메시지 내용으로 여전히 판별 가능 |
| **실패 경로 단일화(상태·메시지 모두 통일)** | **정보 노출 차단, 단순한 멘탈 모델** | **사용자 안내는 다른 수단으로 보완 필요** |

**결정: 실패 경로 단일화.** "없는 이메일", "비밀번호 불일치", "소셜 가입자가 비밀번호 로그인 시도" 세 가지 케이스 모두 동일한 상태 코드와 동일 문구를 반환한다. 사용자 편의성 저하는 클라이언트 측의 "최근 로그인 수단 힌트" UX로 보완한다(후술).

### 2. 타이밍 상수화 (Timing Side-channel 방지)

| 선택지 | 장점 | 단점 |
|--------|------|------|
| 소셜 유저 분기에서 즉시 실패 | 구현 단순 | bcrypt 호출 유무로 시간 차이 발생 |
| 무작위 sleep 삽입 | 구현 간단 | 통계적 분산이 커져 정확도는 낮추지만 완전 차단 아님 |
| **더미 해시 기반 상수시간 검증** | **모든 경로에서 동일한 bcrypt 비용 소모** | **상수 해시의 안전한 관리 필요** |

**결정: 더미 해시 상수시간 검증.** 이메일이 없거나 소셜 유저일 때도 `passwordEncoder.matches(입력값, DUMMY_HASH)`를 1회 호출하여 bcrypt 연산 시간을 항상 동일하게 소모한다. 더미 해시는 실제 비밀번호와 매칭되지 않는 임의 문자열을 사전에 인코딩한 결과를 코드 내 상수로 관리한다(한 곳에서만 사용되므로 민감도 낮음).

### 3. 브루트포스 방어 계층화

| 축 | 기존 | 변경 |
|---|------|------|
| IP 단위 | 분당 N회 | 유지 |
| 계정 단위 | 없음 | **이메일 단위 분당 N회 추가** |

**결정: 계정 단위 Rate Limit 추가.** 다수 IP를 보유한 공격자가 단일 계정에 무제한 브루트포스를 시도하는 것을 차단하기 위해 IP 단위 rate limit 위에 이메일 단위 rate limit을 추가한다. Redis 기반 Lua 원자 스크립트를 재사용하여 TOCTOU를 방지한다.

> 구체적 임계값은 운영 정책이므로 이 문서에서는 추상적으로만 언급한다.

### 4. 회원가입 응답 일관화

| 선택지 | 장점 | 단점 |
|--------|------|------|
| 현상 유지 (영어 메시지, 즉시 409) | 변경 없음 | 언어 불일치, UX 저하, 이메일 열거 가능 |
| 기존 `ErrorCode` 체계로 통일 | 일관성, 한국어 | 이메일 열거 자체는 남음 |
| 확인 메일 기반 가입 | 열거 근본 차단 | MVP 스코프 초과 |

**결정: ErrorCode 체계로 통일.** 기존 `InvalidValueException + ErrorCode` 패턴을 그대로 적용하여 `EMAIL_DUPLICATE`, `NICKNAME_DUPLICATE` 코드와 한국어 메시지로 반환한다. 이메일 열거 자체를 차단하는 "확인 메일 기반 가입"은 MVP 스코프를 벗어나므로 별도 이슈로 남긴다. IP 기반 가입 rate limit은 유지되어 대량 스캔은 제한된다.

### 5. CORS 로컬/개발 프로파일 화이트리스트

| 선택지 | 장점 | 단점 |
|--------|------|------|
| 와일드카드 + allowCredentials | 어떤 로컬 포트든 즉시 동작 | `dev` 프로파일이 실수로 운영에 적용 시 위험 |
| **명시적 origin 목록** | **실수로 프로파일이 잘못 적용돼도 임의 origin 차단** | **새 포트 추가 시 코드 수정 필요** |

**결정: 명시적 origin 목록.** 로컬 프론트엔드가 사용하는 몇몇 표준 포트만 나열하고 나머지는 차단한다. 운영 프로파일은 이미 명시적 도메인 목록을 사용하므로 영향 없음.

### 6. JWT 알고리즘 고정 검토

**결정: 추가 코드 변경 없음 + 방어 의도 주석화.** jjwt 0.12.x에서 `verifyWith(SecretKey)`는 내부적으로 HMAC 계열 알고리즘만 허용하며, "alg: none" 주입 공격이 자동 차단된다. 기존 구현이 이미 안전하므로 코드 변경은 불필요하다. 다만 향후 라이브러리 업그레이드나 키 타입 변경 시 회귀를 방지하기 위해 **이 불변성에 의존하고 있다는 주석**을 파서 메서드에 남긴다.

## 클라이언트 측 보완: "최근 로그인 수단 힌트"

서버 응답에서 정보를 완전히 제거하면, 정작 정당한 사용자가 "내가 이 계정을 어떤 수단으로 만들었더라?"를 잊었을 때 혼란을 겪는다. 이 UX 손실을 **서버 응답 없이** 보완하기 위해 클라이언트 로컬 기록 방식을 도입한다.

**설계**:

- 성공 로그인 시 사용한 수단(`LOCAL` / `GOOGLE` / `KAKAO`)을 기기의 `localStorage`에 기록한다.
- 로그인 페이지 진입 시 기록을 읽어, 마지막에 사용한 버튼 위에 작은 말풍선 힌트(일반화된 문구)를 표시한다.
- 힌트 문구는 "최근에 여기로 로그인했어요"처럼 **어떤 계정이 존재하는지 시사하지 않는 일반 문구**만 사용한다.

**보안적 함의**:

- 이 기록은 **기기별 로컬**이므로 서버·네트워크를 통해 정보가 누출되지 않는다.
- 공격자가 피해자의 기기에 이미 접근 가능한 상황이라면 이 힌트 유무는 의미가 없다(더 큰 문제).
- 힌트 문구가 provider를 명시하지 않기 때문에, 설령 누군가 화면을 훔쳐본다 해도 "이 사람이 어떤 provider를 쓴다"는 정보를 얻지 못한다. (버튼 위치로 유추는 가능하지만 이건 UI 구조상 불가피)

업계 사례: 인프런, 네이버, 프로그래머스 등 다수 한국 서비스가 동일 패턴을 사용한다. Cherry는 "정보 노출 최소화" 원칙을 지키면서도 이 표준 UX를 따른다.

## 트레이드오프

### 감수하는 것

- 소셜 가입자가 실수로 비밀번호 로그인을 시도할 때 화면에 표시되는 메시지는 일반화된 "이메일 또는 비밀번호를 확인해주세요" 뿐이다. 사용자는 SNS 버튼을 직접 다시 눌러야 한다. "최근 로그인 수단 힌트"가 이 마찰을 대부분 상쇄한다.
- 모든 로그인 실패 요청이 bcrypt를 1회 호출하므로, 실패 케이스의 서버 CPU 비용이 약간 상승한다. 단, 이 비용은 애초에 브루트포스 방어 목적과 일치한다.
- 이메일 가입 열거는 `ErrorCode` 단일화로 완전히 차단되지는 않는다(응답 코드만으로도 구별 가능). 이는 "확인 메일 기반 가입" 도입 시까지 남는 알려진 한계이며, IP 단위 rate limit이 최소한의 방어선을 제공한다.

### 얻는 것

- 로그인 API에서 "가입 유형"·"provider"·"계정 존재 여부"를 외부에서 식별할 수 없다.
- bcrypt 타이밍 사이드채널이 제거된다.
- 다중 IP 공격자가 단일 계정에 무제한 브루트포스를 시도할 수 없다.
- 로컬 개발 환경의 CORS가 실수로 운영에 적용돼도 임의 origin을 허용하지 않는다.
- 클라이언트는 서버 응답에 의존하지 않고 최근 로그인 수단을 자연스럽게 안내할 수 있다.

## 대안: 왜 "확인 메일 기반 가입"을 선택하지 않았는가

가입 API의 이메일 열거를 근본적으로 차단하려면, 이미 등록된 이메일인지 여부와 무관하게 "가입 확인 메일을 보냈다"는 동일한 응답을 반환해야 한다. 실제 메일은 신규 이메일에만 발송하고, 기존 가입자의 이메일에는 아무것도 보내지 않는 방식이다.

이 방식은 보안상 가장 강력하지만:

- 현재 MVP에는 트랜잭셔널 메일 발송 인프라가 구축되어 있지 않다.
- 도입 시 가입 UX 자체가 비동기 2단계로 재설계되어야 한다.
- Phase 10의 목표는 "소셜 로그인 통합"이며, 이메일 가입 플로우의 보안 재설계는 별도 Phase로 다루는 것이 적절하다.

따라서 이번 ADR에서는 "ErrorCode 일관화 + IP rate limit 유지"로 현실적 절충을 선택하고, "확인 메일 기반 가입"은 향후 Phase 과제로 보류한다.
